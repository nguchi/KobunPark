## 1. 目的

本書は、KobunParkのMVPで実装する機能、品質、制約および受入条件を定義する。

KobunParkは、JSON、CSV、URL・文字列、LaTeX、正規表現などの構文をローカル環境で確認・整形・検証するmacOSアプリである。MVPでは、日常利用に必要な最小の処理を安全かつ確実に提供する。

## 2. 要件表記

要件IDの接頭辞を次のように定める。

| 接頭辞 | 意味 |
|---|---|
| `FR` | 機能要件 |
| `NFR` | 非機能要件 |
| `SEC` | セキュリティ・プライバシー要件 |
| `UX` | 操作性・アクセシビリティ要件 |
| `CON` | 制約 |
| `AC` | MVP受入条件 |

優先度は次の3段階とする。

- `Must`：MVPの完成に必須
- `Should`：可能な限りMVPに含めるが、完成を妨げる場合は延期可能
- `Could`：将来候補。MVPには原則含めない

## 3. 対象範囲

### 3.1 MVP対象

- macOSアプリ
- JSONの整形と検証
- URLコンポーネントのパーセントエンコード／デコード
- Base64変換、HTMLおよびJSON文字列のエスケープ／アンエスケープ
- CSVからMarkdown表、HTML表、XMLへの変換
- LaTeX数式の入力とローカルプレビュー
- 正規表現の一致確認と置換プレビュー
- 明示的なコピー／ペースト
- 主要操作のキーボード対応
- 変換ロジックの単体テスト

### 3.2 MVP対象外

- iPadOS・iOS版の提供
- Windowsネイティブ版
- JSON・YAML相互変換
- Mermaidプレビュー
- Excel数式・Power Query Mの整形
- スニペット、履歴、文書の自動保存
- iCloudその他のクラウド同期
- Ollamaその他のAI連携
- アカウント、認証、課金
- メニューバー常駐、共有拡張、App Intents

### 3.3 MVP後の変換機能計画

MVP後は、次の変換機能を候補とする。実装順序と詳細仕様は、MVPの安定化と実利用評価後に個別に決定する。

| 分類 | 将来要件 |
|---|---|
| LaTeX | Unicode表現およびMathMLへ変換できる |
| JSON | YAMLおよびXMLへ変換できる |

共通操作は`文字列を貼り付ける -> 形式を自動判定する -> 変換方法を選ぶ -> 結果をプレビューしてコピーする`の4段階とする。自動判定は推奨値であり、利用者が常に上書きできることを要件とする。

### 5.1 JSON受入例

入力：

```json
{"name":"えぬぐち","enabled":true,"items":[1,2]}
```

期待結果（2スペース）：

```json
{
  "name" : "えぬぐち",
  "enabled" : true,
  "items" : [
    1,
    2
  ]
}
```

注記：実際の空白形式は採用するJSONシリアライザーに合わせてテストで固定し、リリース後に無理由で変更しない。

## 6. URLエンコード／デコード機能要件

| ID | 優先度 | 要件 | 検証方法 |
|---|---|---|---|
| FR-URL-001 | Must | RFC 3986のunreserved文字を残し、それ以外をUTF-8バイト単位でパーセントエンコードできる | 単体テスト |
| FR-URL-002 | Must | `%HH`形式をUTF-8文字列へデコードでき、大文字・小文字の16進数を扱える | 単体テスト |
| FR-URL-003 | Must | 日本語、絵文字、空白、改行を壊さず往復変換できる | 単体テスト |
| FR-URL-004 | Must | 不完全または不正なパーセント表記では位置を含むエラーを表示し、入力を保持する | 単体・UIテスト |
| FR-URL-005 | Must | UTF-8として解釈できないデコード結果を出力せず、エラーを表示する | 単体テスト |
| FR-URL-006 | Must | `application/x-www-form-urlencoded`と暗黙に混在させず、デコード時の`+`を空白へ変換しない | 単体・UIテスト |

対象はURL全体ではなくURLコンポーネントとする。エンコード時はスペースを`%20`、`+`を`%2B`へ変換する。

MVPでは、アプリに同梱したKaTeX 0.18.1をWebKitでオフライン描画する。実装と運用上の制約はADR-007に記録する。採用時に確認した項目は次のとおりとする。

- ライセンス条件
- アプリへの資産同梱方法
- ネットワークアクセスが発生しないこと
- 数式エラーの取得方法
- VoiceOver等のアクセシビリティ
- アプリサイズと起動性能への影響

## 14. データモデル

MVPでは入力や履歴を永続化しない。実行中の状態として、少なくとも次を保持する。

### 14.1 共通状態

- 選択中の機能
- 入力文字列
- 結果文字列またはプレビュー状態
- 検証エラー
- 処理中状態
- 最大100操作のUndo／Redo履歴

### 14.2 JSON固有状態

- インデント設定
- 整形／圧縮モード

### 14.3 URL固有状態

- URL、Base64、HTML、JSON文字列の種別
- エンコード／デコードモード
- 変換元文字列
- 変換結果
- パーセント表記またはUTF-8のエラー状態

### 14.4 CSV固有状態

- CSV入力
- Markdown、HTML、XMLの出力形式
- 変換結果
- CSV構文エラー状態

### 14.5 LaTeX固有状態

- LaTeXソース
- インライン／ディスプレイ表示設定
- 描画成功／失敗状態

### 14.6 正規表現固有状態

- パターン
- 対象文字列
- 置換文字列
- 正規表現オプション
- 一致範囲と一致件数
- 置換プレビュー

## 15. エラー処理要件

- エラーは利用者が次の修正行動を判断できる内容にする
- 内部例外メッセージをそのまま表示せず、必要な情報へ変換する
- 行・列・範囲を取得できる場合は表示する
- 入力誤りとアプリ内部障害を区別する
- エラー発生時も元入力を保持する
- 同じ入力で再試行可能にする
- 未対応構文は「無効」と断定せず、未対応である可能性を示す

## 16. テスト要件

各構文処理に次のテスト区分を用意する。

1. 正常系
2. 空入力
3. 不正構文
4. 日本語・Unicode・絵文字
5. 改行コード（LF、必要に応じてCRLF）
6. 境界値または大きな入力
7. 過去に発生した不具合の回帰テスト

テストは、変換結果だけでなく次も確認する。

- 元入力が保持されること
- エラーが明示されること
- 機密となる入力内容がログへ出ないこと
- オフラインで動作すること
- 失敗後に再実行できること

## 19. 未決事項

次は情報不足または技術検証前のため未確定である。

## 20. 変更管理

- `Must`要件の削除・変更は、理由と影響を`docs/DECISIONS.md`へ記録する
- MVP対象外の機能を追加する場合は、納期・テスト・セキュリティへの影響を評価する
- 実装と要件が異なる場合、暗黙に文書を合わせず、どちらを正とするか確認する
- 不具合から新しい恒久要件が判明した場合、本書と回帰テストを同時に更新する
- 製品名、対象プラットフォーム、ネットワーク送信方針の変更には明示的な承認を必要とする
